00Conventions

Settle these once and every module below becomes mechanical to implement and to bind.

Transport & base

  • Base URL: https://api.izigo.app/api/v1 — HTTPS only. The current rider base is http://159.223.19.239/index.php: plain HTTP, raw IP, and index.php in the path. All three need to go before launch.
  • Auth: Authorization: Bearer <access_token> on everything except /config, /pages/*, the auth module, and public package tracking.
  • Headers on every request: Accept: application/json, X-App: rider|driver, X-App-Version, X-Platform: android|ios, X-Device-Id, Accept-Language: fr|en.
  • Bodies: JSON, snake_case keys. File uploads use multipart/form-data.
  • Money: integer minor units + explicit currency (XOF has no minor unit — send whole numbers). Never floats.
  • Time: ISO-8601 with offset (2026-08-12T14:03:00Z). Server is the clock — the clients currently derive trip state from local wall-clock time and that has to stop.
  • Phone: E.164 (+2250700000000).
  • Coordinates: lat / lng as decimals, 6 places.

Response envelope

{
  "success": true,
  "data": { ... } | [ ... ],
  "meta": { "page": 1, "per_page": 20, "total": 143, "last_page": 8 }
}

// error — same shape, always
{
  "success": false,
  "error": {
    "code": "RIDE_ALREADY_CANCELLED",       // stable, machine-readable
    "message": "This trip was already cancelled.",  // localised, safe to show
    "fields": { "phone": ["Phone already registered."] }  // 422 only
  }
}

Status codes: 200 ok, 201 created, 204 deleted, 400 bad request, 401 expired/absent token, 403 role or KYC not permitted, 404, 409 state conflict (accepting an expired job offer), 422 validation, 429 rate limited, 503 maintenance mode.

Rules that save rework

  • Idempotency: every POST that creates money or a trip (/rides, /packages, /co-ride/bookings, all wallet and payment calls) must accept Idempotency-Key and replay the original response. Riders double-tap on bad networks.
  • Server owns fares. The client currently computes prices locally. Every price shown must come from a signed, expiring quote_id, and the trip must be created from that quote id, not from a client-sent amount.
  • Pagination: ?page= & ?per_page= on every list, with the meta block above.
  • Lists accept ?status=, ?from=, ?to=, ?vertical= where sensible.
  • Soft enums: clients must tolerate unknown enum values without crashing — send new statuses freely, but never rename existing ones.
  • No secrets in the app. Payment gateway keys, map keys and SMS credentials stay server-side. See Security fixes.

SHAREDOne Trip, One Identity — and the State Map

This section is identical in the rider and driver contracts. It is the seam where the two apps meet: get it wrong and both sides work perfectly on their own while never seeing each other.

One row, one id, one name

A ride is a single row in a single table. The rider app and the driver app are two views of it, not two objects that need reconciling.

  • Canonical identifier: trip_id, prefixed trp_. Both apps receive it under that exact key. Do not expose a separate ride_id to one app and a job_id to the other — they were named differently in earlier drafts of these two documents, and that mismatch is precisely what this section exists to close.
  • Driver paths keep their noun. /driver/jobs/{id} stays as written — "job" is the driver's word for their side of the trip — but the {id} passed is the trip_id. One value, addressable from either app's routes.
  • One realtime room: presence-trip.{trip_id}. Both parties join the same channel with the same string. Driver position, chat and state changes all flow through it.
  • The rider-facing code (ZR-4801, ZD-1234-5678) is a display label for support and receipts. It is never the key, never in a URL, and never used to join a channel.

The state map

The server owns one state machine — the sixteen-state driver machine. What the rider sees is a projection of it, not a second machine kept in sync. Compute the rider status from the trip state on the way out; never store both.

Everything about offering, declining and expiring is invisible to the rider by design. A trip can be offered to four drivers and declined by three while the rider sees one uninterrupted “finding you a driver”. Leak those transitions into ride.status_changed and the rider watches their trip flicker between states for reasons they cannot see — and support inherits the calls.

Two things endpoints alone will not give you

  1. A dispatch engine. Every route in these contracts can be implemented correctly and a rider will still sit on “finding a driver” forever, because which drivers get offered a trip, in what order, within what radius, and what happens on decline or timeout is business logic, not a route. The config for it is specified (offer_timeout_seconds, search_radius_m, strategy, max concurrent offers); the algorithm is yours to write, and it is the actual product.
  2. Cold-start recovery. Both apps must be able to rejoin a trip already in progress after a crash, a kill or a dead battery — GET /rides/active and GET /driver/jobs/active. Without them a dropped connection ends the trip from that side's point of view while the other side keeps going.

  5. Payment gateway of record. CinetPay for all mobile money, or CinetPay + Wave direct? And who owns refunds — gateway or wallet credit?

  7. Cash handling. On a cash trip the driver holds the platform's cut. Confirm the settlement mechanic and the cash cap that blocks going online — the driver wallet already displays "Pending Cash Settlement".
  8. Dispatch rules. Offer timeout (15 s?), sequential or broadcast-to-many, search radius, and how many drivers see one job. This determines whether accept can 409 and how the offer sheet behaves.

27Security Fixes to Land With v1

Found while mapping the clients. All four ship inside the app bundles today.

  • Live payment credentials in the app. A CinetPay apikey + site_id and a Wave bearer token sit in the rider app's mobile_payment_repo.dart. Anyone can pull them out of the APK. Rotate all three and move initiation behind /payments/intents.
  • Google Maps key exposed. The same key is committed in .env and hardcoded in the driver app's app_constants.dart. Rotate it, restrict it by package name + SHA-1 and per-API, and proxy the billable calls through /geo/*.
  • Plaintext HTTP. The base URL is http:// against a raw IP. Tokens and locations over cleartext — TLS and a real domain before any real traffic.
  • Client-computed prices. Fares are currently calculated in the client. Move that to the server and make trips creatable only from a signed quote id, or fares become editable by anyone with the APK.
